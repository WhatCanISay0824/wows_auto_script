# 托管期间键鼠协作方案

日期：2026-10-31

状态：供评审的方案文档，未修改运行代码、配置或现有预览。

## 1. 结论与目标

可以放宽“托管时不能使用键鼠”的操作限制。建议采用协作托管：用户使用电脑时，脚本让出键鼠；用户返回游戏并交还控制后，脚本重新识别画面，继续当前会话。

这能让用户在托管过程中查看 GUI、使用浏览器、写文档，以及临时接管游戏。代价是用户占用键鼠期间，脚本不再执行开火、切换视角、地图选点、退出战斗或开始下一场等输入操作。游戏中已经生效的自动驾驶可能继续运行，但脚本不能保证战斗表现和场次推进完全不受影响。

如果目标是“一边正常使用其他软件，一边让脚本持续控制游戏并自动开始下一场”，需要输入与画面的独立环境。仅调整现有暂停规则无法实现这一点。

本方案首先解决日常使用限制，不引入后台消息输入、驱动或虚拟机。下面区分已经存在的能力、拟议行为和实施前必须验证的条件。

## 2. 当前限制来自哪里

### 2.1 脚本与用户共享系统输入

现有默认后端 `SendInputBackend` 使用 Windows `SendInput`；备选后端 `SetCursorPosBackend` 仍然移动系统光标，键盘事件也继续使用 `SendInput`。这些调用没有提供独立的游戏键鼠通道。

脚本会移动光标、点击、按键和滚动。在用户同时使用同一桌面的情况下，可能发生以下冲突：

- 用户正在输入文字，脚本恰好发送消耗品按键。
- 用户正在拖动窗口，脚本移动光标或点击。
- 用户刚切到其他应用，尚未取消的脚本动作仍然执行。
- 用户手动打开游戏地图，脚本仍按原来的步骤发送开关地图按键。

因此，限制的根因是控制权冲突，不能通过删掉“失焦暂停”或恢复光标位置解决。

### 2.2 已有前台检查还不足以支持自由切换

`src/main.py` 的运行循环目前约每秒检查一次游戏窗口，游戏不在前台时请求暂停。`InputExecutor` 在动作发送前检查输入门禁、批次是否失效以及动作是否过期，但当前接口没有逐动作复核目标窗口前台状态的规则。

这意味着已有失焦处理是基础保护，不能据此承诺用户任意切换窗口后绝不会收到在途输入。检查焦点与实际发送事件之间仍可能发生窗口切换；复合点击内部也包含移动、按下、等待和释放多个步骤。

现有状态机对部分窗口原因暂停已经支持回到游戏前台后自动恢复。需要改进的是让出控制、恢复条件和界面状态的一致性，而不是重新发明整套暂停机制。

### 2.3 游戏画面也受桌面使用影响

ISS-011 的实机记录表明，现有窗口截图曾持续返回冻结旧帧，因此全屏场景改为优先截取桌面上的游戏区域。桌面截图会受到其他窗口遮挡、游戏最小化及显示方式变化的影响。

脚本在后台继续“截图成功”，不等于取得了可用于游戏判断的新画面。不能把浏览器覆盖的游戏区域送入死亡判定、退出授权或导航逻辑，也不能仅给旧图像加上新时间戳就称为实时监测。

## 3. 方案比较

| 方案 | 用户能做什么 | 游戏自动化的连续性 | 改动与主要限制 | 建议 |
| --- | --- | --- | --- | --- |
| 协作托管 | 查看 GUI、使用其他应用、临时接管游戏 | 会话保留，用户占用输入期间暂停脚本操作；返回后继续 | 复用门禁、释放和恢复流程，补齐控制权及截图有效性判断 | 本项目优先采用 |
| 同一桌面后台控制 | 用户使用其他应用，同时希望游戏持续自动化 | 取决于游戏是否接受后台输入和后台画面 | 需单独证明后台消息输入与截图可用；现有代码和实机证据不支持此承诺 | 暂不采用 |
| 独立运行环境 | 用户使用本机，游戏及脚本在另一台设备或独立环境中运行 | 输入互不争用时可持续自动化 | 额外设备或环境成本；虚拟化的显卡、游戏兼容性和截图仍需验证 | 确实需要长时间并行使用时考虑 |

推荐协作托管，是因为它直接改善使用体验，并保留当前经过修复的截图、导航和输入执行链路。其局限也很明确：允许用户随时使用电脑，不等于脚本在同一时刻仍能完整操作游戏。

## 4. 推荐行为：会话持续，输入按控制权执行

### 4.1 控制状态

在脚本生命周期和游戏流程之外，增加一个明确的输入控制状态。它只表达谁有权产生新的业务输入，不另建一套游戏流程状态机。

| 控制状态 | 脚本行为 | 界面显示 |
| --- | --- | --- |
| 脚本控制 | 游戏在前台、画面有效，允许生成和执行新动作 | 托管中 |
| 正在让出 | 关闭门禁，取消未执行动作，请求释放脚本按下的键鼠 | 正在让出输入 |
| 用户使用电脑 | 保留会话，停止游戏输入，不推进依赖游戏画面的步骤 | 等待游戏前台 |
| 用户接管游戏 | 游戏可以在前台，但脚本仍不输入，直至用户交还 | 手动接管 |
| 重新核对 | 检查焦点、画面、场次和按键释放状态，重新建立动作 | 正在恢复 |

安全暂停、停止和错误状态继续沿用现有生命周期。等待前台或手动接管不能覆盖已有的安全暂停原因。

等待时保留会话编号、本场编号、用户指定目标和已有记录。无需结束会话，也不把临时离开记为战斗中断。会话时长、允许时段等按真实时间计算的限制继续计时；具体结算依据仍由真实画面和现有业务规则决定。

### 4.2 查看本工具

延续已确认的 GUI 设计：用户点击性能、数据、日志或设置时保持会话运行，脚本让出游戏输入，不反复抢回焦点。

性能监测、日志写入和界面更新继续运行。小地图显示最近一张有效游戏画面，并保留原采集时间和真实帧龄。同场画面可以提交归一化目标位置，执行前必须取得提交后的新战斗画面并复核；旧画面不能作为发送游戏输入的依据。

如果 GUI 遮住游戏区域，不能承诺地图仍能实时刷新。第一阶段不为保持地图刷新而新增一套后台捕获方案。

### 4.3 使用浏览器或其他应用

建议把“切到其他应用就进入脚本暂停”放宽为“保留会话并等待游戏前台”。无论用户切去哪个普通应用，都先关闭游戏输入。

等待期间不自动切回游戏，不抢光标，不自动发起下一场。游戏自行航行、战斗结束等变化可以发生，但只有返回游戏、取得有效新帧后，脚本才据此继续处理。

用户主动把游戏切回前台后，可在满足恢复条件时自动继续。如果先前发生的是用户主动暂停、手动接管、安全异常或紧急停止，则不能仅因焦点返回就恢复。

这项行为与现有 GUI 设计中“切到其他应用仍暂停”的规则存在取舍。本方案建议采用新的等待行为，但本轮只形成提案；在用户确认并实施前，已有规则不因此改变。

### 4.4 临时接管游戏

增加“接管”操作，位于现有运行控制区域。用户点击后，脚本先取消业务输入并释放自身持有的键鼠，得到确认才显示“手动接管”。此时用户可以在游戏中调整视角、手动航行、打开地图或处理其他界面。

用户完成后点击“交还托管”，脚本核对当前游戏画面再继续。不能采用“鼠标几秒没动就恢复”的默认规则，因为用户可能正在观察、阅读或等待。

接管期间继续保留本场已有目标。交还时不立即重发该目标，避免立刻覆盖用户刚完成的操作；原先尚未完成的地图序列和自动重设任务取消。本场默认不再周期性覆盖航向；用户通过 GUI 提交新目标后，才恢复该目标的管理。下一场重新使用默认导航策略。

该规则使“交还”恢复其他托管流程，而不会立即把人工调整撤销。界面仅需显示“导航：手动调整”，无需增加常驻解释文字。

用户在接管期间可能手动离开战斗、回到港口或开始新的战斗。恢复时必须依据现有画面与本场上下文处理；无法判断是否仍为原场次时保持暂停，不把新战斗直接归入旧记录。

### 4.5 修改单个航行目标

继续采用上一轮确认的单目标点替换，不引入多途经点。

用户在 GUI 中提交目标后，可授权一次切回游戏并执行地图点选。若这时用户仍在其他应用中工作，则目标保持待处理，不主动抢回焦点；GUI 自身前台时的点击提交才构成该次切回授权。

执行前重新检查当前场次、目标请求是否最新、画面与标定是否有效。输入控制权已让出、安全暂停或停止时取消执行。请求失效应显示原因，不在数分钟后无提示地突然补发。

## 5. 为什么第一阶段不做“用户一动鼠标就自动接管”

自动识别人工输入可以进一步减少操作，但它不适合作为第一阶段唯一的保障。

1. 检测到用户点击时，点击本身可能已经进入游戏，脚本在途动作也可能已经发送。检测不能撤销这些事件。
2. 当前 `GetAsyncKeyState` 用于安全热键，不能仅靠它可靠区分所有人工输入和脚本输入。轮询光标位置也会把脚本自己的移动当作用户操作。
3. 窗口钩子或 Raw Input 需要新增事件来源、线程和验证；注入标记可以帮助排除脚本事件，但需要覆盖当前两个后端、不同权限和外设情形，不能直接等同于完整的人工输入识别。
4. 即使识别成功，脚本与用户同时按同一个键时，系统仍没有独立的“各自持有一份按键”状态。脚本释放自己按下的键，也可能影响用户的连续操作。

因此第一阶段采用明确接管，以及焦点变化后自动让出。可选的“按住某个键接管”应在热键冲突和独立监听验证后再加入，不占用现有 F11、F12。

第二阶段若用户仍觉得操作繁琐，可以评估人工输入触发让出。它应作为额外便利：不屏蔽用户事件，检测后迅速关闭脚本输入，并保持接管直至显式交还；不能宣称首次人工事件绝不会与脚本相撞。

## 6. 输入与恢复的具体规则

### 6.1 两条让出路径

用户准备长时间打字、拖动或手动操作游戏时，推荐先点击“接管”，看到确认后再操作。这条路径可以先完成脚本释放，减少与人工按键重叠。

用户直接切换到其他应用时，系统自动让出作为便利路径。需要新增前台变化通知，并在输入线程实际发送每个业务动作前复核焦点，不能只依赖现有约一秒一次的窗口检查。

通知和发送前检查仍不能把“检查焦点”和“SendInput 实际生效”变成一个不可分割的系统操作。因此只能承诺尽快终止后续输入，不能承诺所有切换瞬间零误输入。发现问题的实机记录应决定是否进一步限制直接切换路径。

### 6.2 取消与释放

让出开始时先关闭业务门禁，再使在途批次失效并清空待执行业务动作，由唯一输入线程释放脚本记录为已按下的键鼠。

不能等待整个业务批次完成后才让出，也不能因动作优先级较高就继续发送菜单或退出点击。已经进入后端的复合动作需要允许取消尚未执行的输入步骤；已经按下的键鼠仍需走释放清理。

释放动作是清理操作，不因游戏失焦而被业务前台检查拒绝。不得遍历并释放用户所有物理按键，也不恢复“脚本开始前的光标位置”，以免把用户光标拉走。

UI 显示“输入已让出”必须依据实际释放结果。当前释放处理会记录释放次数，即使底层释放发生错误；实施时应区分请求已处理与释放成功，不能直接把计数增加当成成功证明。

### 6.3 返回后的检查

只有等待前台状态可以随用户主动返回游戏自动恢复。建议初始采用以下恢复条件，具体时间属于待验证的工程参数：

- 游戏窗口存在、未最小化，前台状态连续稳定约 500 毫秒。
- 没有仍然有效的手动接管、暂停、停止或错误原因。
- 脚本涉及的按键、鼠标按钮和修饰键没有尚未结束的人工按住状态；不能在用户拖动期间恢复。
- 取得返回前台之后的有效新帧，窗口几何与标定仍适用；不要求画面必须发生像素变化，因为静止画面也可能有效。
- 重新识别当前状态和场次，取消旧步骤，按新画面生成动作。

仅按键状态复核不能发现全部人工意图，因此显式手动接管始终具有更高优先级。

恢复检查失败时保持等待或转入带具体原因的暂停，不反复试图抢焦点。手动接管后的交还也执行同样检查。

### 6.4 调度与记录

用户占用输入期间停止产生业务动作，不把它们缓存到返回后集中执行。随机行为重新安排下一次执行时间，不补发漏掉的开火或消耗品动作。

业务步骤的等待时间与整个会话的真实时间分开处理。输入等待期间不因“地图迟迟没关”“按钮迟迟没点”误触发恢复流程；会话时长、允许时段与安全监测仍正常运行。

后台运行循环持续处理控制命令、记录和自身心跳，不把无效游戏截图当作正常观察结果。运行循环确实阻塞时仍由原看门狗处理，不能另起线程假装业务循环健康。

日志记录让出原因、释放结果、等待时长、恢复来源和重新识别结果。数据面板显示本次等待时长，帮助解释为什么会话仍在运行但场次暂未增加。

## 7. 界面与安全规则

运行控制增加一个随状态变化的按钮：“接管”或“交还托管”。已有暂停、恢复和停止保留，各自语义明确：

- 接管：会话保留，由用户控制游戏；显式交还后继续。
- 暂停：脚本暂停，按原暂停原因决定是否允许恢复。
- 等待前台：用户使用其他应用，返回游戏且检查通过后可自动继续。
- 停止：结束托管并清理，不退出游戏，不自动重启。

状态栏只显示当前真实状态，不堆叠操作说明。过载保护阈值仍按上一轮决定保持待确定，本方案不替用户设定阈值。

F12 紧急停止保持全局可用且不可恢复。它可能与其他应用的 F12 功能冲突，第一阶段不自动更换快捷键。F11 按当前 `SafetyMonitor` 的实际代码是暂停后的恢复热键，不能仅凭运行循环里的注释把它当作已实现的暂停与恢复开关。它也不自动承担交还手动接管的含义。

优先级为停止与严重异常、已有安全暂停、手动接管、等待前台、正常托管。任何较低优先级事件都不能解除较高优先级限制。恢复时重新核对全部有效原因，避免一个“焦点返回”事件错误打开输入门禁。

## 8. 其他技术路线为什么暂不采用

### 8.1 直接取消前台检查

它会让现有全局输入落入其他应用，并没有解决控制权问题。输入后端和截图限制都仍存在，因此不采用。

### 8.2 使用 PostMessage 或 SendMessage

向指定窗口发送消息不等同于游戏接受后台控制。当前没有实机证据证明游戏对后台鼠标、扫描码、全屏地图和菜单操作均有效；只验证一个按键也不能证明整条业务链路可用。

如果以后确实需要评估，应先用独立验证任务覆盖地图开关、目标点击、菜单退出、港口选船和连续多场，再决定是否建立新后端。不能先替换后端再把失败补成大量例外。

### 8.3 另接一套键鼠或使用双显示器

普通 Windows 桌面仍共享前台窗口与系统光标。第二套外设和第二块屏幕改善显示与操作便利，但不会自动产生独立的输入会话。双屏也不证明现有截图链路支持被遮挡或最小化的游戏。

### 8.4 更换截图技术

其他捕获技术可以作为画面问题的候选方案，但需要验证 D3D 游戏、遮挡、最小化、帧新鲜度和 Python 集成成本。即使后台截图成功，也没有解决键鼠共享，因此不作为本次放宽限制的前置重构。

### 8.5 使用独立设备或虚拟化环境

独立设备可从根本上分离用户桌面与游戏输入，适合持续多场自动化与日常工作必须同时进行的场景。需要额外硬件、运行环境和单独维护。

虚拟机不直接等于可用方案，仍需验证显卡性能、游戏运行支持及输入和截图行为。普通远程桌面或第二个登录会话也不能未经验证就视为独立、稳定的游戏环境。本轮不安装、配置或连接这些环境。

## 9. 建议实施范围

第一阶段集中处理以下内容，不改变导航算法和数据库结构：

| 范围 | 必要改动 |
| --- | --- |
| 运行服务与 GUI | 发布输入控制状态，新增接管与交还命令，保留会话与场次上下文 |
| 窗口与输入执行 | 前台变化通知、逐动作前台复核、取消在途步骤、真实释放反馈；保持唯一输入出口 |
| 感知与状态机 | 后台无有效游戏画面时不推进游戏判断，返回后重新识别；取消旧步骤，保留安全暂停 |
| 导航与随机行为 | 接管后不自动覆盖人工航向，不补发漏掉的动作；新场次恢复默认策略 |
| 日志与数据展示 | 记录让出、等待和恢复；显示小地图真实帧龄 |

该方案比单纯修改焦点判断更大，但每项改动都直接服务于已确认的真实冲突。可以先完成 GUI 内查看与显式接管，再放宽到其他应用的自动等待与恢复；第一步验证失败时，不提前开放第二步。

当前只是设计提案。没有取消前台保护，没有启用后台输入，也没有改写上一轮已经确认的行为。

## 10. 验收标准与证据要求

| 场景 | 应观察到的结果 |
| --- | --- |
| 点击接管，再切到编辑器输入文字 | 先得到释放确认；之后没有脚本按键、滚轮、点击或光标移动进入编辑器 |
| 在动作间隙和按键保持期间切换应用 | 后续业务动作取消，脚本持有的键鼠释放；记录检测与释放时间，并说明仍存在的切换竞态 |
| 多次快速切换游戏、GUI 与其他应用 | 不反复抢焦点、不补发旧动作、不因重复事件错误恢复 |
| 用户手动操作游戏地图后交还 | 不盲目补发 M 键；重新识别，不立即重设为原目标 |
| 用户在其他应用中停留至本场结束 | 会话保留；返回后按真实画面处理，不在后台盲点下一场或误写战斗结束 |
| 游戏被覆盖、最小化或截图冻结 | 不依据无效帧作死亡、退出和导航判断；地图保留原时间并显示真实帧龄，目标执行前复核新画面 |
| 返回时仍按住鼠标或修饰键 | 不自动恢复业务输入；释放并通过其他检查后才允许恢复 |
| 手动暂停、安全异常或 F12 后返回前台 | 焦点返回不能取消已有暂停；F12 后不能恢复 |
| 释放失败 | 界面不能显示已让出，错误有明确记录；恢复保持禁止 |
| 接管期间手动开始另一场战斗 | 不把新战斗算作原场次；无法确认时暂停并保留诊断依据 |

离线验证覆盖控制原因优先级、动作失效、释放失败、恢复条件和旧画面拒绝。实机验证同时检查游戏行为与其他应用是否受到脚本输入影响，不能仅凭模拟输入后端的调用次数宣布完成。

测量前台变化到门禁关闭、输入释放、恢复完成的时间分布，不预先承诺没有证据支持的固定延迟。验证未通过前，保留现有严格模式作为默认行为。

## 11. 推荐决策

建议按第一阶段范围采用协作托管，优先保证用户能可靠地让出与取回控制；确认实机表现后，再把其他应用前台时的行为由暂停调整为等待与自动恢复。

如果后续目标升级为“使用其他软件期间，游戏仍必须自动开火并连续开始下一场”，再评估独立运行环境，而不是继续削弱同一桌面的输入保护。
