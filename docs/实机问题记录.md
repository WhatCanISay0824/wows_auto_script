## ISS-001：进入战斗后未设置自动驾驶，船停在原地

**发现时间**：2026-10-30 23:48～23:52
**主要证据**：`logs/session_20261030_234652.log`（会话 8）
**关联截图**：`screenshots/diagnostics/20261030_235214_pause_pause_restart_mid_battle_detected_BATTLE.png`

### 现象

1. 23:48:18 状态机 `QUEUEING -> BATTLE_ACTIVE`（战斗识别已生效）；
2. 23:48:19 autopilot 启动，记录我方出生点（小地图归一化）`(0.354, 0.548)`；
3. 23:48:20 / 23:49:57 / 23:51:57 共发出 3 次 `autopilot_click`：
   目标归一化 `(0.5, 0.4523)` → 屏幕坐标 `(2300, 1312)`；
4. 23:52:14 诊断帧显示：船速 **STOP 0.0 kts**、船停在原地、小地图无自动驾驶目标线。

### 影响

船不移动、不参战，可能被判挂机、无收益；后续开火/消耗品行为也失去意义。

### 初步分析（未验证，供修复时排查）

1. **主假设**：本客户端/设置下**小地图左键点击不会设置自动驾驶**。官方交互提示出现在
   **全屏地图（M）**上（历史截图 211242/211253：“左键点击来设置自动驾驶模式下的航向”）。
   → 需要验证「按 M 打开全屏地图 → 左键点击目标 → 按 M 关闭」能否设置航向。
2. 点击时机：首次点击在进入战斗约 2 秒，可能处于开场镜头/输入锁定阶段；
   后续 2 次点击在 23:49:57、23:51:57，仍需确认是否被游戏接收。
3. 前台/输入目标：日志本次没有失焦暂停，但未记录每次点击时游戏是否前台
   （若点击时前台不是游戏窗口，SendInput 可能只激活窗口而不被游戏处理）。
4. 坐标换算：`(2300,1312)` 落在实测小地图区域内，但仍需“点击后截图”确认是否出现目标线/航向标记。

### 修复验收标准

- 进入战斗后 ≤5 秒内成功设置航点；
- 船速 > 0 且向目标区域移动，小地图出现自动驾驶目标线/标记；
- 连续 3 场复现通过。

### 修复前置

先做**手动对照实验**（同一坐标：小地图点击 vs 全屏地图点击），确认正确交互方式；
需要实机截图/录屏证据后再改代码。

## ISS-002：血条未归零时尝试退出战斗（硬性约束）

**用户要求（硬约束）**：**血条未到 0（未死亡）时绝对禁止退出战斗**；只有确认血条归零后
才允许按 ESC / 点“离开战斗”。战斗自然结束（出现结算界面）后按结算流程回港，不属于“提前退出”。

### 当前实现风险（代码审计，本次未修改）

1. 死亡判定是**多信号投票**：`hp_bar_absent`、`hp_zero`、`banner`、`marker_lost`、`spectator_ui`，
   达到权重/稳定帧数即进入 `DEAD_PENDING_EXIT`，随后 `EXIT_MENU_OPEN` 发送 ESC。
2. `hp_zero` 使用 `profile.yaml: battle_hud.hp_fill_zero_ratio = 0.05`，即血条填充 **≤5% 就判为“零”**；
   船在 1%～5% 残血时仍然存活，可能被误判死亡 → 提前退出。
3. `hp_bar_absent`（换船/模板失配/光照变化）、`marker_lost`（小地图标记识别失败）、
   `banner`（死亡提示误匹配）都可能**单独或组合**触发退出。
4. 日志证据：会话 8 在 23:52:58 `death_detected`（明细 `hp_zero=True`）→ 23:53:00 发送 ESC →
   23:53:01 点击“离开战斗”。该次是否确实 0 血需回看当时帧；用户观察到“未归零就退出”，
   与“5% 阈值/其它信号误判”假设吻合。

### 影响

违反用户硬约束；在仍存活时退出会中断本局收益，且中断人工接管。

### 修复方向（待评审后实施）

1. **退出战斗门禁与“血条确认为 0”强绑定**：`hp_zero` 需满足填充比例接近 0（例如 ≤0.005）
   且连续稳定 N 帧，最好同时能读到血量数字为 0；
2. `hp_bar_absent` / `marker_lost` / `banner` **不得单独触发退出**，只可作为“疑似死亡”记录或降权；
3. 战斗内未知画面/识别超时**不得**用 ESC 退出，只允许重试识别；
4. 退出前写证据：HP 区域裁剪、投票明细、连续帧数、当时截图（诊断目录）；
5. 新增配置（如 `exit.require_hp_zero: true`）并同步写进 profile 与设计补充文档。

### 修复验收标准

- 构造 HP>0（含 1%～5% 残血）、模板失配、标记丢失等场景，脚本**绝不**发送 ESC / 点击“离开战斗”；
- HP=0 时正常退出；
- 连续 3～5 场实机无提前退出现象。

## ISS-003（运行时/测试流程）：后台启动被终止后子进程残留，导致双实例

**发现时间**：2026-10-30 23:47～23:54

### 现象

通过后台任务启动脚本后调用“终止”，`py` 启动器被结束，但 `python -m src.main` 子进程仍然存活并
继续控制游戏；随后又启动了一个新实例，同一时间存在**两个脚本实例**（任务管理器可见 4 个进程：
2 个 `py` + 2 个 `python`）。本次观察到的“进战斗后不动/被退出”来自残留的旧实例（会话 8）。

### 风险

两个实例同时发送键鼠输入，行为不可预测，调试结论被混淆。

### 修复方向（待办）

1. 单实例锁（lock file / Windows mutex），启动时发现已有实例直接退出并提示；
2. 终止时结束进程树（Windows Job Object，或 `taskkill /T`），不要只杀父进程；
3. 开发脚本避免直接 kill 启动器父进程。

### 当前处置

已手动结束全部残留进程（4 个）；重启前确认任务管理器中没有 `src.main` 的 python 进程。
