## 项目基本情况与分析范围

项目通过截屏、模板匹配和模拟键鼠，完成港口校验、选船、排队、战斗操作、死亡退出和回港续场。
运行入口为 `src/main.py`，默认使用不依赖地图包的 `autopilot` 导航；需要地图识别和航线数据的
`waypoints` 模式保留为可选功能。当前属于实机联调阶段，不能依据离线测试通过认定全流程可用。

现有结构已经按职责拆分：`perception` 负责画面识别，`state_machine` 决定流程，`navigation`
和 `behavior` 产生动作，`execution` 串行发送输入，`storage` 保存本地日志。配置以 YAML 为准，
SQLite 仅记录运行数据。GUI 应复用这些模块，并保留命令行入口。

本次阅读范围包括 README、项目综述、工作约定、实机及标定记录、实现计划、初步与详细设计 Word
文档及设计评审补充；重点检查主循环、状态机、死亡判定、导航、输入队列、暂停恢复、选船和事件日志
之间的调用关系。文档采用“最新用户约束与实机证据优先，其次为实现补充，再其次为详细设计”的口径。

分析遵守现有边界：本地单窗口运行，不读取游戏内存、不联网控制、不引入 OCR，不保存登录凭据，
不代登录，不自动出售船只或装备。经济加成保持原样；装备校验只要求信号旗数量为零。

以下区分三种证据：已有实机记录、本次历史截图或日志复核、本次离线复现及完整代码调用路径。
离线复现均使用假依赖或记录型输入后端，不发送真实键鼠输入。本次没有启动游戏执行新一轮实机验收。
代码位置以本次基线为准。

## ISS-001：进入战斗后未设置自动驾驶，船停在原地

**发现时间**：2026-10-30 23:48～23:52
**主要证据**：`logs/session_20261030_234652.log`（会话 8）
**关联截图**：`screenshots/diagnostics/20261030_235214_pause_pause_restart_mid_battle_detected_BATTLE.png`

### 现象

1. 23:48:18 状态机 `QUEUEING -> BATTLE_ACTIVE`（战斗识别已生效）；
2. 23:48:19 autopilot 启动，记录我方出生点（小地图归一化）`(0.354, 0.548)`；
3. 23:48:20 / 23:49:57 / 23:51:57 共发出 3 次 `autopilot_click`：
   目标归一化 `(0.5, 0.4523)` → 屏幕坐标 `(2300, 1312)`；
4. 23:52:14 诊断帧显示：船速 **STOP 0.0 kts**、船停在原地、小地图无自动驾驶目标线。

### 影响

船不移动、不参战，可能被判挂机、无收益；后续开火/消耗品行为也失去意义。

### 根因（2026-10-30 用户确认）

**自动驾驶的正确交互方式：先按 `M` 打开放大的全屏地图，再在地图上左键点选目标点。**
直接在战斗画面右下角的小地图上点击**不会**设置航向——当前实现（`AutoPilotNavigator` 直接点击
小地图坐标）就是错误的交互方式，所以 3 次点击全部无效、船停在原地。

待后续修复（本次不修改）需要覆盖的点：

1. 按 `M` 打开全屏地图 → 等待地图界面就绪 → 在目标位置左键点击 → 再按 `M` 返回战斗视角；
2. 全屏地图有独立的缩放/平移/居中规则，目标点坐标需要按**地图视图**重新换算（不能直接复用
   小地图内容区坐标）；
3. 必须保证按键释放、关闭地图、以及地图界面遮挡期间不误触其它战斗输入；
4. 点击后需要验证航向是否生效（小地图目标线/船速>0），失败可重试；
5. 旧的“直接点小地图”路径应废弃或作为可配置备选（不同客户端/版本可能不同）。

### 2026-10-31 实机复跑结果（M 点选已生效，验证逻辑误判）

用户实机运行（会话 13，`logs/session_20261031_133854.log`）中，装备页校验通过后正常进入战斗；
第一次 M 全屏地图点选后：

- **实际已生效**：战斗 HUD 显示 `M 自动驾驶开启`，船速 `19.3 kts`（FULL），小地图出现自动驾驶目标虚线；
- 但旧验证逻辑连续 3 次判失败并降级 `surface=minimap`：`displacement_px=0/2/1`（8 秒内小地图位移
  远小于阈值 3px）、`speed_mps=0.0`（舰船定位速度估计样本不足，未能给出实际约 10 m/s）；
- 结论：M 地图点选/坐标换算本身可用，**误判来自验证判据**（阈值/估计方法），不是交互失败。

修复：从该实机战斗帧提取 `autopilot_indicator`（“M 自动驾驶开启”静态文字，35×150 像素），
配置为 `navigation.autopilot_verify_feature: autopilot_indicator`；验证时优先用该特征确认航向，
位移/船速保留兜底（可配 null 关闭特征验证）。模板在后续战斗帧匹配 0.9902；下次运行验证不再误降级。

### 其他待确认（非根因）

1. 点击时机：首次点击在进入战斗约 2 秒，可能处于开场镜头/输入锁定阶段（等后续修复时一并验证）；
2. 前台/输入目标：日志本次没有失焦暂停，但未记录每次点击时游戏是否前台；
3. 全屏地图的坐标换算需要一张实机“M 地图 + 点击后目标线”的截图/录屏作为标定依据。

### 修复验收标准

- 进入战斗后 ≤5 秒内成功设置航点（按 M → 点选 → 关闭地图）；
- 船速 > 0 且向目标区域移动，小地图出现自动驾驶目标线/标记；
- 连续 3 场复现通过。

### 修复前置

根因已由用户确认，无需再做小地图/全屏地图对照实验；修复前需补充一张实机“M 全屏地图”截图用于
坐标标定，并按“先改设计补充文档、再改代码”的流程执行（本次不修改）。

## ISS-002：血条未归零时尝试退出战斗（硬性约束）

**用户要求（硬约束）**：**血条未到 0（未死亡）时绝对禁止退出战斗**；只有确认血条归零后
才允许按 ESC / 点“离开战斗”。战斗自然结束（出现结算界面）后按结算流程回港，不属于“提前退出”。

### 现象与本次复核

会话 8 的日志在 2026-10-30 23:52:58 记录 `hp_zero=True`、`hp_bar_absent=False`，随后进入
`DEAD_PENDING_EXIT`；23:53:00 进入退出菜单流程，23:53:01 进入点击“离开战斗”后的确认状态。

本次人工查看对应诊断截图 `screenshots/diagnostics/20261030_235258_death.png`：
画面左下显示血量 `32,794 / 41,200`，自身船只仍存活，血条呈黄色。使用当前铁公爵配置和
`PerceptionEngine._hp_zero_ratio()` 对同一张 2560×1600 截图重新计算，结果为 `0.0`，
低于配置阈值 `0.05`。这是存活画面被判为零血的直接证据，不只是残血情况下的推测。

### 代码原因与影响范围

1. `src/perception/engine.py:539` 的 `_hp_zero_ratio()` 计算的是“指定区域内满足绿色 HSV
   范围的像素数 / 区域总像素数”。它不是数值血量比例。`profile.yaml:39` 至 `:42` 只配置了
   绿色范围；黄色血条不在范围内，绿色像素为零仍会被当成零血。
2. `src/perception/engine.py:579` 使用严格的 `ratio < 0.05` 判断；把阈值改为 `0.005`
   仍然会把本次 `0.0` 的存活画面判为零血，不能单靠降低阈值修复。
3. `src/perception/death.py:273` 允许 `hp_zero` 或 `hp_bar_absent` 任一信号稳定 1.5 秒后
   直接判死，并将结果锁存。`marker_lost`、`banner` 等不是当前配置下各自独立的强信号，
   但可以参与加权投票。模板失配和血量归零仍未在决策上严格区分。
4. `src/state_machine/machine.py:578` 只检查 `death.dead` 就启动死亡退出；`:850` 的等待结束后
   直接进入菜单，没有再次确认当前血量。误判一旦成立，后续存活证据不会撤销退出。
5. 没有船只血条模板时，`configure_ship_hp_bar()` 只禁用“血条消失”信号；
   `check_death()` 仍可能运行绿色像素判零。现有“未提供血条模板时只靠死亡提示或结算”的说明
   与该行为不一致。
6. `src/state_machine/machine.py:1011` 的异常恢复在无法识别画面时仍可能发送
   `recovery_escape`。这本身只证明可能打开菜单，不能据此断言该分支一定完成离开战斗；
   但它不符合“战斗内未知画面不自动发送 ESC”的约束。

### 影响

已观察到船仍有大量血量时启动退出操作，违反用户硬约束，并中断当前战斗。
现有日志只能确认该次启动了菜单和返回港口操作，不能把“进入 EXITING 状态”等同于已经成功回港。

### 修复方向（待评审后实施）

1. 将血量证据区分为“确认存活、确认归零、无法判断”。颜色变化、区域遮挡、模板缺失和画面异常
   都不能自动等价为归零；先使用本次黄色血条和不同剩余血量截图验证识别方案。
2. 在保留“不引入 OCR”的范围内，采用经过样本验证的血条有效性和空血识别；若不能可靠证明归零，
   保守等待自然结算。不得把死亡提示、血条消失或小地图标记丢失直接当作提前退出授权。
3. 将归零证据与提前退出门禁绑定，在进入退出流程和发送退出操作前校验来源、连续帧和新鲜度。
   血量转为存活或未知时撤销尚未执行的退出动作。
4. 战斗内未知画面只重试识别或暂停；导航开关地图使用 `M`，避免借用退出菜单键。
5. 留存血条裁剪、原始像素比例、判定依据和时间戳；识别分数不能在 GUI 中显示成实际血量。

### 修复验收标准

- 本次 `32,794 / 41,200` 黄色血条截图必须被判为存活；绿色、黄色、红色及残血样本均不得提前退出。
- 模板缺失、遮挡、标记丢失、过期帧和未知画面不触发退出；误判后的新存活证据能取消待执行动作。
- 可靠确认归零时正常退出；无法确认时等待自然结算，结算回港流程仍可用。
- 离线回归后连续 3～5 场实机通过，分别覆盖死亡和存活到结算；未实机验证前不标记已解决。

## ISS-003（运行时/测试流程）：后台启动被终止后子进程残留，导致双实例

**发现时间**：2026-10-30 23:47～23:54

### 现象

通过后台任务启动脚本后调用“终止”，`py` 启动器被结束，但 `python -m src.main` 子进程仍然存活并
继续控制游戏；随后又启动了一个新实例，同一时间存在**两个脚本实例**（任务管理器可见 4 个进程：
2 个 `py` + 2 个 `python`）。本次观察到的“进战斗后不动/被退出”来自残留的旧实例（会话 8）。

### 风险

两个实例同时发送键鼠输入，行为不可预测，调试结论被混淆。

### 修复方向（待办）

1. 单实例锁（lock file / Windows mutex），启动时发现已有实例直接退出并提示；
2. 终止时结束进程树（Windows Job Object，或 `taskkill /T`），不要只杀父进程；
3. 开发脚本避免直接 kill 启动器父进程。

### 当前处置

已手动结束全部残留进程（4 个）；重启前确认任务管理器中没有 `src.main` 的 python 进程。

## ISS-004：暂停释放键鼠后，旧动作仍会继续执行

### 触发条件与证据

在输入队列已有动作时暂停或失焦。`machine.py:1075` 调用 `executor.release_all()`；
`src/execution/queue.py:201` 只向队首加入释放批次，没有增加动作代次 `epoch`、清空队列，
也没有禁止后续提交。`:416` 的动作循环仍把同一代次的旧批次视为有效。

本次使用阻塞第一条动作的记录型后端，在第二条动作入队后请求释放，观察到执行顺序：
`in_flight → RELEASE → queued_before_pause`。未发送真实键鼠输入。

### 影响、建议与验收

暂停不能保证停止输入；已排队的点击、滚轮或按键可能在用户切回桌面后继续执行。
当前正在执行的单个后端调用无法仅靠队列撤回，剩余动作和未开始批次则应立即失效。

建议为暂停建立统一输入门禁：拒绝新业务动作、使旧批次失效、清空待执行动作、优先释放键鼠，
恢复时只接受重新识别后生成的新动作。验收应覆盖在途批次、排队批次、重复暂停和恢复，
确认释放之后不会执行暂停前遗留的业务动作。

## ISS-005：F12 和心跳超时不能独立阻止输入

### 触发条件与证据

主循环卡在截屏、识别、数据库等待或其他耗时调用时按 F12，或触发心跳超时。
`src/main.py:193` 装配 `SafetyWatchdog(safety)` 时没有传入事件回调；
`src/execution/safety.py:306` 只向 `StopController` 写入请求，`:386` 在没有回调时直接返回。
实际停止和释放依靠 `main.py:307` 的主循环下一次同步请求。

本次按同样装配方式，使用假按键源触发 F12，控制器已显示 `stop_requested=True`，
但主循环尚未同步时，独立输入线程仍执行了随后提交的记录型动作，释放计数为零。
这证明停止请求未独立接入输入门禁；本次未测量真实游戏中的停止延迟。

### 影响、建议与验收

主循环不返回时，F12 和心跳超时不能保证及时停止队列输入。GUI 若直接复用该路径，
“停止按钮已点击”也不能代表输入已经停止。

建议让安全监控直接触发线程安全、非阻塞的输入取消请求，状态机转移和日志收尾仍由运行线程负责，
不从监控线程直接发送游戏操作。验收应故意阻塞主循环，确认独立输入门禁拒绝新动作、
旧批次失效并由输入线程完成释放，同时记录实际响应时间和释放是否成功。

## ISS-006：暂停状态不同步，恢复会丢失当前战斗

### 触发条件与证据

这里有两条相关但不同的路径：

1. 状态机的装备校验失败、中途战斗识别和窗口检查直接调用 `request_pause()`，没有同步
   `SafetyMonitor.controller`。F11 在 `safety.py:306` 中只清除控制器的暂停状态；
   控制器原本未暂停时，不会产生恢复事件。`main.py` 的 `was_paused` 也就不会转发恢复。
   本次复现中，正式状态机为 `PAUSED`，控制器却为未暂停，按 F11 产生零个恢复事件。
2. `machine.py:1084` 无论手动恢复还是窗口恢复都转回 `INIT`；`:377` 清空 `_battle` 和
   `_battle_id`，没有先结束当前记录；`:385` 在看到战斗画面时又以 `restart_mid_battle` 暂停。
   本次使用现有测试依赖驱动到战斗中，暂停再恢复后，战斗编号从 `22` 变成 `None`，
   状态再次为 `PAUSED`，原战斗没有写结束记录。

### 影响、建议与验收

部分暂停无法通过 F11 恢复；当前会话战斗中的短暂失焦被当作全新进程中途接管，导致无法继续，
并丢失场次关联。已有“窗口恢复自动继续”不能理解为已经支持战斗内恢复。

建议统一暂停原因和恢复请求来源，区分“当前会话可恢复”和“新进程不接管已有战斗”。
当前会话恢复须重新验证画面并保留场次编号；不能恢复时明确提示接管或等待结算，
对中断记录明确收尾，不能静默清空。验收覆盖港口、排队、战斗、装备失败和心跳暂停，
确认 GUI、F11 与自动失焦暂停的状态一致，重复恢复不创建或遗失场次。

## ISS-007：目标船卡片可见不等于已选中，隐藏卡片也无法正常搜索

### 触发条件与证据

`src/state_machine/ship_check.py:153` 把 `ship_card` 匹配成功直接视为当前船正确，
`:186` 的 `tick()` 随即返回 `OK`。目前模板刻意避开选中边框，搜索区域覆盖底部整排轮播条，
而两艘船的 `loadout_slots` 都为空；因此目标船只要在列表中可见，就可通过该校验，
没有先点击目标卡片，也没有验证“当前选中船”的独立证据。

使用实际铁公爵配置、正式 `ShipChecker` 和“只报告目标船卡可见”的假感知复现：
直接返回 `status=ok`，选船动作为空。主流程 `machine.py:431` 先做装备检查再进入船只校验，
所以目标船尚未选中时，先前信号旗检查还可能针对另一艘船。

另一路径中，当前 `profile.ship_selection_sequence` 按底部轮播条设计为空。
`ship_check.py:238` 的 `_start_selection()` 却在序列为空时把剩余滚动次数改为零。
使用正式步骤执行器和“目标卡不可见”的假感知复现：配置允许滚动 20 次，但首轮没有滚动动作，
内部立即失败，原因为“船只列表滚动到底仍未找到配置船只”。该轮返回状态仍为 `SELECTING`，
下一轮才返回 `FAILED`。

### 影响、建议与验收

目标船可见但未选中时可能用当前另一艘船开局，且装备检查没有覆盖最终选中的船；
目标卡不可见时会在没有滚动搜索的情况下失败。已有铁公爵实机成功记录不覆盖这两个条件。

建议流程调整为“查找并点击目标船 → 用新画面确认已选中 → 检查该船信号旗 → 开局”。
空选择序列只表示无需额外打开列表，不应取消滚动预算。验收至少覆盖目标可见但未选中、
目标在屏幕外、找不到目标和选船后信号旗非零，确认不选错船、不跳过最终装备校验。

## ISS-008：未处理异常会跳过统一清理

### 触发条件与证据

`src/main.py:612` 先调用 `_run_session()`，正常返回后才调用 `_teardown()`，
二者没有由 `try/finally` 绑定。`_run_session()` 的 `finally` 只停止看门狗；
`_build_runtime()` 又在完整装配结束前启动了日志与输入线程，中途装配失败也没有统一回收路径。

本次在主入口中替换运行时构造，并让 `_run_session()` 抛出 `RuntimeError`，
观察到 `_teardown()` 调用次数为零。未创建真实输入后端。

### 影响、建议与验收

异常路径不保证停止输入线程、关闭截屏资源和收尾日志。命令行进程若随异常直接退出，
不能据此断言线程一定长期残留；但 GUI 会继续存活，该缺口会直接影响再次启动和窗口关闭。

建议运行时构造支持部分失败回收，会话运行使用 `try/finally` 执行幂等清理，
并把异常原因交给界面显示。验收在构造各阶段、感知、状态机和运行循环中注入异常，
确认已创建资源全部回收、输入释放，并且只有清理完成后才允许重新启动。

## ISS-009：输入线程连续失败后，上层没有暂停

### 触发条件与证据

`src/execution/queue.py:483` 在连续达到失败阈值后设置 `_failed=True`、清空待执行队列，
后续 `submit()` 拒绝动作，并记录“上层应释放输入并进入 PAUSED”。
但 `_build_runtime()` 没有配置错误通知，`_run_session()` 和状态机也没有消费
`executor.failed` 或 `last_error`。输入线程仍可等待新任务，不会因设置 `_failed` 自动进入退出收尾。

### 影响、建议与验收

后续业务动作会被拒绝，但上层可能仍显示正在运行，并继续等待界面变化直到其他超时触发恢复。
若此前有分离的按下动作成功、释放动作失败，当前路径也没有主动安排一次释放。
该条由完整代码路径确认，本次没有制造真实 SendInput 失败。

建议把输入失败接入统一暂停和释放路径，展示具体失败原因；恢复前明确重新初始化或校验后端状态。
验收使用会连续失败的假后端，确认失败后不再产生业务输入、上层及时暂停、尝试释放且原因可见。

## ISS-010：回调事件没有关联当前战斗编号

### 触发条件与证据

`src/main.py:89` 的 `_EventBridge` 将 `battle_id` 初始化为 `None`，

## ISS-011：窗口截屏返回冻结帧，装备页校验无法通过（2026-10-31 实机发现）

**发现时间**：2026-10-31 13:11～13:15（用户实机复跑，连续在 PORT 装备页校验暂停）
**关联日志**：`logs/session_20261031_131142.log`、`131459.log`、`131526.log`
**关联诊断截图**：`screenshots/diagnostics/20261031_131533_pause_pause_loadout_check_failed_...png`

### 现象

每次运行都在 `PORT -> loadout` 阶段失败：`click port_equip_tab at (1058,112)` 报告成功，
随后等待 `loadout_signal_flags` 超时，进入 `PAUSED(loadout_check_failed)`；诊断截图里游戏仍显示港口页。

### 实机取证

1. 用桌面 DC（`GetDC(0)` + `BitBlt`）截取真实屏幕：点击“装备”后游戏**已经切换到装备页**，
   截图里可见“配件和升级品 / 武器 / 消耗品 / **信号旗 0/8**”；
2. 在真实装备页截图上匹配模板 `loadout_signal_flags`：**score=0.9979**，中心 `(1122,706)`，
   完全落在配置 region `[0.38,0.41,0.50,0.47]` 内——模板与区域本身没有问题；
3. 项目 `GdiCapture` 的窗口 BitBlt 每次返回**同一张冻结的港口页画面**（跨多次运行、多个进程字节一致），
   `PrintWindow(PW_RENDERFULLCONTENT)` 兜底同样不更新；画面均值/方差正常，旧的黑屏校验无法发现。

### 根因

无边框全屏的 D3D 窗口（窗口类 `App`）在窗口 DC 上 `BitBlt` 得到的是 DWM 缓存的旧表面，
`PrintWindow` 对 flip-model 交换链返回静态帧；旧实现只在“黑屏/纯色”时才尝试 PrintWindow，
因此**“有效但冻结”的帧会被当作正常画面**，状态机永远看不到页面切换（点击其实已生效）。
该问题也会影响战斗内 HUD/死亡判读，属于 P0。

### 修复（2026-10-31）

- 新增 `perception.capture_method: auto | window | screen`（默认 `auto`）：
  - `auto`：客户区覆盖整个虚拟屏幕（面积 ≥95% 且原点误差 ≤2px）且游戏在前台时，
    **优先**用桌面 DC 按客户区屏幕位置 BitBlt（`GdiFrameSource.grab_screen`）；
    成功后固定桌面截屏（`screen_only`），避免每帧先拿到冻结帧；
  - 桌面截屏失败时回退旧的窗口 BitBlt/PrintWindow；非全屏窗口保持旧行为；
  - `window`=强制旧行为；`screen`=强制桌面截屏（远程桌面/特殊环境）。
- `src/main.py` 与 `src/tools/check_env.py` 传入该配置；新增纯函数
  `is_fullscreen_client_rect()` 与桌面截屏单测（窗口 BitBlt 黑屏/冻结、非全屏、强制 screen、
  失败回退等场景）。

### 验证与边界

- 离线：`tests/test_capture_geometry.py` 新增桌面截屏与回退测试，全部通过；
- 实机：新路径 `screen_only=True`，截屏均值与真实桌面一致；装备页 `loadout_signal_flags`
  实机命中 0.999（修复前为 0.278 永远不命中）；
- **端到端重跑待验证**：需用户重启脚本确认能通过装备页校验并完成一场联合作战；
  桌面截屏要求游戏窗口在前台（脚本已有失焦暂停策略），多显示器/窗口化场景沿用旧路径。

## GUI 升级简要设计（建议稿，未实施）

### 目标与第一版范围

将现有命令行脚本升级为 Windows 本地控制台，方便选择配置、运行控制、观察状态和进入标定工具。
成功标准是操作更直观、运行状态可判断、停止和清理可验证，同时复用现有识别与状态机逻辑。

第一版包含客户端选择、输入船名自动查找、首次导入船卡截图、本地账号别名选择、场次和时长限制、配置校验、
启动／暂停／恢复／停止、状态与日志展示，以及船卡、界面区域和自身标记的标定入口。
账号仍由用户在游戏内手动登录，GUI 只选择本地档案；第一版优先跑通单账号，轮换随后接入。
不扩展多窗口并发、账号代登录、远程控制和在线服务。

### 技术方案比较

| 方案 | 适用点 | 成本与限制 |
| --- | --- | --- |
| Tkinter + ttk，本地桌面窗口 | Python 标准库方案，足够承载表单、按钮、状态和日志；符合现有轻量依赖方向 | 复杂图像标注和大型表格能力有限；须先检查本机 Python 是否带 Tk 支持 |
| PySide6，本地桌面窗口 | 多页面、复杂表格和集成图像标定更方便 | 新增 Qt 依赖和打包体积，需要验证 Python 3.14 与工具链兼容性 |
| 本地网页 + Python 后端 | 页面布局灵活，可用浏览器呈现 | 增加本地服务、前后端通信和进程管理，对当前单机控制台范围偏重 |

建议第一版采用 Tkinter + ttk，船卡导入直接放在运行页，其他标定先复用现有工具入口。
现有 `calibrate_ship` 和 `calibrate_common` 已使用 Tkinter 窗口及 OpenCV 图像处理，可复用其能力。
若后续明确需要在同一窗口内反复编辑区域和模板，再评估 PySide6。此处仅为技术建议，
本次不安装依赖、不更换现有框架，也不承诺打包兼容性已验证。

### 界面组织

| 区域 | 主要内容 | 操作约束 |
| --- | --- | --- |
| 运行页上部 | 客户端、船名输入框、导入船卡截图、本地账号别名、最大场次和时长 | 船名支持已有记录补全；新船引导导入截图；运行期间禁止修改本次配置 |
| 运行页中部 | 校验、启动、暂停、恢复、停止；提示 F12 紧急停止 | 校验通过且无活动运行实例才可启动；停止不等于离开战斗 |
| 运行页状态区 | 运行生命周期、游戏流程状态、暂停原因、完成场次、前台状态、最近帧时间、导航反馈 | 将“点击已发出”和“航行已确认”分别展示；识别分数不显示为实际血量 |

无需每个功能开独立窗口。主窗口用页签组织，运行控制和关键暂停原因应始终容易找到。
不默认置顶盖住游戏，不在运行时自动弹出会抢焦点的日志窗口。

### 简化选船：输入船名与导入船卡截图

#### 现有能力与简化目标

用户日常只需在 GUI 中输入船名并点击“启动”，脚本负责查找和选择，不要求用户填写内部船只编号、
创建目录、编辑 `ship.yaml`，也不要求每次打开独立标定工具。首次缺少识别材料时，直接在同一页面补充。

当前 `src/main.py:449` 的 `_resolve_ship()` 只是在已有档案的名称中查找，再取得对应模板，
并没有从游戏画面读取任意船名的能力。`calibrate_ship` 已有读图、裁剪、质量检查和保存逻辑，
适合改造成面向普通用户的导入流程，但这些自动化封装目前尚未实现。

#### 方案比较与推荐

| 方案 | 用户操作 | 新增条件或成本 | 本次建议 |
| --- | --- | --- | --- |
| 输入船名，使用游戏内置搜索 | 输入任意船名，脚本在游戏搜索框输入并选择结果 | 必须先确认港口确有可用搜索控件、中文输入方式、结果唯一性及选中确认；目前未验证 | 后续若实机证实可行，可优先采用，不一定需要新增依赖 |
| 输入船名，首次导入船卡截图 | 已登记船只只输入名称；新船首次导入一次图片 | 复用现有 OpenCV、Tkinter 和 YAML，不新增第三方库或在线服务 | 第一版推荐，可直接沿用现有识别方法 |
| 输入船名，识别画面文字 | 脚本滚动列表并识别每张卡片的船名 | 需增加中文 OCR 能力，可能涉及识别库、模型或系统语言包，以及准确率和 Python 3.14 兼容性验证 | 作为备选评估，不纳入第一版，不改变当前“不引入 OCR”的边界 |

推荐把名称输入和截图导入做成一个连续流程：已有记录时直接复用；没有记录时提示导入。
只依赖现有模板匹配时，船名是本地图片的检索名称，不能凭空生成一张与游戏一致的船卡。
“完全不登记，只输入任意名称”需要验证游戏搜索或另行引入文字识别，不能当作现有能力承诺。

#### GUI 操作流程

1. 在运行页输入船名，例如“铁公爵”。已有记录显示名称、客户端和船卡预览，用户无需接触内部编号。
   名称匹配优先精确匹配；简称或部分名称对应多艘船时列出候选，不自行猜选。
2. 没有记录时显示“导入船卡截图”。这里的导入是选择本机图片，不发送到服务器。
   已裁好的船卡可直接使用；导入完整港口截图时，在内嵌预览中框选一次目标卡片。
   第一版不承诺自动从任意整张截图中分割出目标船卡。
3. 预览建议保留船体剪影和船名，避开会变化的选中边框、奖励标记和悬浮提示。
   检查图片可解码、尺寸、细节和清晰度；照片、聊天软件缩放图或其他分辨率素材不保证匹配。
   图像质量合格只说明适合作为候选模板，不表示已经在游戏中验证识别成功。
4. 点击“保存并使用”，程序自动生成内部编号，保存当前客户端下的模板和最小船只记录。
   名称由用户输入，不依赖 OCR 自动读出；同名记录更新时提供明确的替换选择，不静默覆盖。
5. 点击“启动”，GUI 完成已有的配置检查并返回游戏前台，脚本自动寻找、选择目标船。
   下次仍只输入船名即可使用；游戏界面更新导致模板失效时，可从同一入口重新导入。

船卡用于港口选船，不需要用户同时提供战斗血条截图或空装备截图。信号旗仍使用客户端统一检查；
没有可靠血量证据时按 ISS-002 等待自然结算，不能因导入船卡就声称支持死亡后提前退出。
第一版还需为“确认当前已选中”建立统一客户端特征；若该特征无法可靠验证，应在首次预览中请求
一次明确确认或停止，不能把“目标卡可见”当作已选中。

#### 自动查找与选中确认

查找过程复用 `ShipChecker` 和输入队列，先处理 ISS-007 的逻辑缺口：

1. 确认当前为港口且船只轮播区域可用，在当前可见区域匹配目标模板。
2. 未找到时将光标移到轮播区域后滚动，每次等待新画面再匹配；搜索应从可确认的列表起点开始，
   或先向一端查找再反向覆盖，不能因目标在初始位置左侧就直接报告不存在。
3. 根据列表不再变化判断端点，并设置总超时和滚动次数上限。筛选条件不由脚本擅自改动；
   未找到时提示检查筛选、模板和舰船是否可用，不通过无限滚动或放宽阈值猜选。
4. 找到唯一可信候选后点击，再等待点击之后的新帧，使用选中高亮、详情面板变化等经实机标定的
   独立特征确认选中。相似卡片出现多个可信候选时暂停并显示预览。
5. 确认目标已选中后再检查该船的信号旗数量，只有检查通过才点击加入战斗。

停止、失焦和 F12 能中断搜索及滚动；“预览查找结果”模式只查找并展示候选，不自动加入战斗。
该模式用于首次验证导入图片是否能识别；正式运行仍可自动完成选船，无需每场人工确认。

#### 保存范围与验收

模板和最小记录继续保存在 `profiles/<client>/ships/<自动生成编号>/`，复用 `card.png`、
`ship.yaml` 的现有约定；客户端默认提供轮播区域和滚动参数，用户不逐船填写。
图像导入职责可放在拟议的 `src/gui/ship_import.py`，复用 `calibrate_common` 的读图和质量检查；
实际查找与选中确认仍归现有船只流程，不放进 GUI 回调。运行中禁止导入写入。

验收需覆盖：已有名称直接使用；首次仅输入名称和导入图片即可保存；中文名称、重名和重复导入；
完整港口截图框选；模糊或尺寸不合适的图片被明确提示；目标在轮播条两侧、被筛选隐藏或根本不存在；
相似卡片不误选；找到但尚未选中不通过；选中之后才检查信号旗；查找期间可随时停止。
至少用两艘船实机交替验证，不能只用“目标本来已经选中”的场景验收。

### 架构与文件职责

先从 `src/main.py` 提取可复用的运行服务，GUI 和命令行都调用同一服务。
GUI 不直接调用 `SendInput`，也不另外实现一套状态转移。

以下是拟议结构，不表示这些目录或接口已经存在：

```text
src/
  main.py                  命令行参数与提示，调用共享运行服务
  runtime/
    service.py             运行时装配、会话生命周期、命令处理和统一清理
    messages.py            控制命令、运行快照和事件的数据类型
  gui/
    main.py                GUI 启动入口与主窗口
    run_page.py            配置选择、运行控制和状态展示
    log_page.py            有限长度日志与场次事件展示
    tools_page.py          校验、标定与本地目录入口
```

现有 `state_machine` 仍负责游戏流程；`runtime` 管理启动、暂停、停止和清理。
界面显示的运行生命周期建议为“已停止、启动中、运行中、已暂停、停止中、等待手动切号、错误”，
另行展示 `PORT`、`BATTLE_ACTIVE` 等游戏状态。这样“游戏仍在战斗”和“脚本已经停止控制”不会混淆。

数据流为“用户操作 → 运行服务 → 现有状态机与输入模块”；
返回流为“运行快照、状态事件和日志 → 消息队列 → GUI”。

### 线程、暂停和停止

GUI 主线程只处理控件和消息展示；单独运行线程承载现有主循环，保留已有输入线程、日志线程和
安全监控线程。运行线程不直接修改控件，界面通过 `after()` 定时读取快照；日志采用有界缓存，
防止长时间运行拖慢窗口。主循环、截屏和等待均不得放进 GUI 主线程。

运行服务建议提供 `start(options)`、`pause()`、`resume()`、`stop()` 和只读快照接口。
启动必须幂等防重入，并在实际控制端使用跨进程单实例锁，防止另一个 GUI 或命令行实例同时控制。
运行选项作为本次会话覆盖值传入，默认不重写 YAML；启动前展示账号覆盖后的实际客户端、船只和上限，
避免界面所选项与加载结果不一致。

暂停、失焦、F12、心跳和输入失败共用一套控制来源。暂停时先关闭业务输入门禁，再取消旧动作并释放；
恢复时先确认游戏前台和画面，再恢复允许的当前流程。点击 GUI 会使游戏失焦，因此“恢复”按钮应明确
发起一次返回游戏前台的操作，前台确认失败就维持暂停；运行中不反复抢回用户主动切走的焦点。
F11 只负责恢复，不把它显示为暂停开关键。

“停止”仅表示停止脚本控制、释放键鼠、收尾本地记录，不发送退出战斗操作。
F12 和停止请求必须能独立取消输入，不能等待一次耗时识别结束才生效。GUI 显示“停止中”直到输入线程
确认释放、运行线程及日志资源完成回收，随后才显示“已停止”并允许再次启动。

关闭窗口时发起同样的停止流程并异步等待。若底层调用卡住且未能完成清理，保持明确的未完成状态，
提供日志位置并禁止再启动，不能仅隐藏窗口后留下控制线程。第一版不使用无法保证资源清理的强杀线程。

### 日志、标定与错误处理

保留当前文本日志、SQLite 和诊断截图，GUI 订阅结构化事件；每条状态变化带会话、场次和时间，
具体动作仍以实际执行与反馈为准。启动失败展示配置文件、字段和原因，运行失败转入暂停或错误，
保留诊断位置，不能吞掉异常后只显示空白状态。

标定第一版复用 `src.tools.calibrate_ship`、`calibrate_profile` 和 `capture_marker`。
船卡导入复用其中的图像与保存逻辑，直接嵌入运行页；其他工具暂时保留自己的图像交互窗口，
GUI 提供选图、参数和启动入口。有写入的工具只在运行停止后启动，
完成后重新校验并刷新档案列表。工具若单独启动进程，使用当前解释器的完整路径并跟踪进程生命周期，
不再经过 `py` 启动器，也不与自动化同时操作游戏。全屏地图标定是 ISS-001 后续修复的独立前置工作，
不能因为已有工具入口就标记为已经支持。

账号轮换接入时，将阻塞的控制台 `input()` 改为“等待手动切号”状态；只有用户在 GUI 确认、
游戏窗口和港口均检查通过后才启动下一账号会话。界面不增加密码或令牌输入框。

4. 接入其余标定工具入口，再加入手动账号轮换。可执行文件打包放在真实流程验收后单独评估。

GUI 验收至少包括：重复点击启动仍只有一个控制实例；命令行与 GUI 同时启动受到互斥限制；
运行时窗口保持响应；切到 GUI 后立即停止业务输入；恢复保留合法的当前场次；
主循环阻塞时 F12 仍能关闭输入门禁；异常、关闭窗口和重复启停均完成释放与清理。

功能验收必须重新覆盖实际的全屏地图点选、船只选择后信号旗检查、黄色和残血不退出、
死亡退出、自然结算及连续 3～5 场。离线测试、按钮响应和日志出现均不能替代这些实机结果。
