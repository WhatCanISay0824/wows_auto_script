# 第三场死亡后停止的修复方案

## 目标与证据

用户设置托管 10 场，但最近会话在第三场后不再继续。本轮保留原有场次、每日、时长和人工停止限制，修复死亡退出与结算交接，不新增非核心功能。

日志 `session_20261101_172836.log` 对应会话 24。前两场正常死亡回港，场间等待分别为 4.20 秒、7.19 秒。第三场在 17:50:15 由血条归零证据触发退出，17:50:17 点击离开战斗，随后连续产生确认菜单补点；17:50:22 未找到确认按钮而进入等待回港。17:53:22 等待回港超时，恢复识别已得到 `BATTLE_FINISHED`，仍以 `recovery_mid_battle` 为由暂停。18:12:56 用户手动停止，数据库记录前两场完成，第三场被中断。

超时截图明确显示结算页及“继续战斗”“回到港口”按钮。对该图使用现有生产模板离线匹配：结算栏 0.9832、继续战斗按钮 0.9549、回港按钮 0.9995，均超过配置阈值。停止由退出状态缺少结算分流导致，不是已证实的场次输入丢失或固定三场上限。日志中的 `max_battles: 20` 是全局安全上限，本次显式场次通过运行器独立设置。

无法仅凭现有截图确定当时为何未识别到退出确认框，也不能把连续补点直接认定为未回港的唯一原因。已确认的代码问题是补点按每次决策发送，未使用配置中的 `post_click_wait_ms`，且没有确认截图已更新。

## 技术方案

沿用 Python 状态机、已有模板、唯一输入线程和结算处理器，不新增依赖，不降低模板阈值，不改账号限制。

1. 在 `EXIT_MENU_OPEN`、`EXIT_CONFIRMING`、`EXITING` 中检查本会话结算页。必须仍有当前场次上下文；识别到结算后清除尚未发送的退出动作，设置本场结果，进入 `BATTLE_FINISHED`。这一分流优先于 ESC、退出点击及退出超时。
2. `EXITING` 区分“从死亡退出等待回港”与“结算按钮已点击等待跳转”。后者保留现有下一场/回港识别，不因结算画面暂留而每帧重入结算或重发按钮。需要重试时仍由既有超时与恢复频率限制约束。
3. 异常恢复识别到结算时，仅在有本会话当前场次且结算证据存在时进入结算处理。无场次上下文、未知画面和存活战斗仍按现有暂停规则，不接管外部战斗。
4. 退出菜单补点复用 `exit.post_click_wait_ms`（至少 500 毫秒）并等待新截图。首次菜单点击与确认流程共享最后点击的帧信息，重复处理同一帧不补发点击。确认框出现后仍优先处理确认，不因菜单残留匹配而点击错误目标。超时计时不得被每次补点重置。
5. 保留结算前检查上限的行为。十场目标应在实际完成十场后停止，较低安全上限、人工暂停/停止和紧急停止依旧优先。启动日志额外记录显式场次目标与全局安全上限，避免把两者混淆。
