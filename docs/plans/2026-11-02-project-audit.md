# 项目检查与修复方案

## 范围与证据

检查现有文档、全部运行模块和测试，保留此前未提交修改。先运行全部现有测试及 Ruff，再审查状态流转、运行服务、感知加载、输入门禁和数据展示之间的调用关系。本次不操作真实游戏、不更改依赖、凭据、数据库结构或 Git 历史，不提交和推送。

初始全套检查为 1167 项通过、1 项因本地样本缺失跳过；Ruff 通过。通过离线调用复现以下缺口，不能依据现有检查通过认定实际流程无问题。

1. 开局序列仍等待排队时，画面已到战斗 HUD，状态停在 PORT、没有场次记录。历史日志 `session_20261101_225803.log` 中也出现了等待队列失败、重走加入战斗失败、随后以无场次上下文为由暂停的路径。
2. 未指定本次目标、只使用全局安全场数上限时，结算按钮选择没有计算当前场完成后的场数，可能先点继续战斗，随后因达到上限停止并把游戏留在排队。
3. 暂停恢复为 BATTLE_ACTIVE 后 `pause_reason` 仍是 manual，GUI 继续展示已过期的暂停原因。
4. GUI 前台等待后返回已打开的退出菜单或确认框时，`continue_after_gui` 不接纳这两个已有状态，转入 gui_return_unknown 暂停。
5. Windows 下 `cv2.imread` 不能读取包含中文的本地路径，已写出的中文文件读回为 None。运行时界面模板、地图底图、己方标记三处仍使用该接口；项目移动到中文目录会影响这些资源加载。
6. 会话快照的今日用量直接复制启动计划，运行中不会随新场次更新。正式 SessionController 已有带缓存的每日查询接口，可复用。
7. 在本进程的存活战斗中手动打开退出确认框，暂停并恢复，原路径会进入 EXIT_CONFIRMING，下一步可生成确认退出点击，缺少本场死亡退出上下文检查。该路径已用真实状态机配合假感知复现；本次没有在游戏中发送该点击。

## 设计取舍

采用局部修正和失败回归，不统一降低阈值、不取消暂停保护、不替换状态机或图像识别技术。放宽通用恢复次数不能修复上述根因，大范围重构会增加本轮验证成本。

### 状态衔接与上限

修改 `src/state_machine/machine.py`。仅在本进程已启动开局序列的 PORT/starting 或 start_full 阶段，允许已有 `_handle_start_coop` 根据实际队列、加载或战斗画面创建场次并继续；成功后取消旧步骤，不再重发加入战斗。首次启动的 INIT 和无上下文战斗恢复规则保持不变。测试同时覆盖快速及完整路径、实际步骤执行器、未知画面继续等待以及有效上下文只创建一次。

结算选择在当前累计完成数加一达到全局安全上限时改点回港；轮换、本次目标和现有会话检查保持原规则。测试使用真实 SessionController 验证最终计数、回港后停止及未到上限仍继续。

成功离开 PAUSED 后清空旧暂停原因；恢复被拒绝则保留新的失败原因。GUI 返回允许已有退出菜单和确认状态，沿用退出处理器，确认框已出现时不得发送 Esc。接纳退出界面必须存在本场已经获准死亡退出的上下文。追加检查已复现：存活时手动打开退出确认框，再暂停恢复，原恢复路径也会直接进入退出确认状态；同样加上本场死亡退出上下文要求。未识别界面仍暂停，人工暂停和停止优先。

### 图片加载与快照

新建 `src/common/images.py`，只负责通过 Path.read_bytes、NumPy 字节视图与 OpenCV 解码读取 BGR 图片。替换 `src/perception/templates.py`、`map_identify.py`、`ship_locate.py` 的三个文件读取入口，保留原缺失、损坏、过小和纯色校验，避免感知模块依赖工具模块。

修改 `src/runtime/runner.py` 的 `_session_view`，优先读取真实 SessionController 的带缓存每日用量，测试替身未提供接口时保留计划值兼容。该数值仍表示每日安全上限使用的已开始场次，不改成已完成数，不更改数据库统计口径。

## 验收结果

1. 原实现定向回归中 14 项失败；另补存活时暂停恢复退出确认框的用例，原实现同样失败。均先保留失败证据再修复。
2. 最终全套测试 1187 项通过、1 项跳过。跳过项依赖已缺失的旧本地死亡截图。命令为 `py -3.14 -m pytest --basetemp pytest_work/project_audit_1102/final_suite --disable-warnings --maxfail=6`。新增 20 项检查覆盖实际开局进度、未知画面等待、全局场次上限、恢复原因、退出上下文、中文图片及损坏资源、今日用量刷新。原中断回港测试曾保留上一场队列和战斗特征；已改为实际港口特征，与它声明的港口画面一致。
3. Ruff 全项目检查和 `git diff --check` 通过。铁公爵配置 0 错误、5 个既有警告；列宁格勒配置 0 错误、4 个既有警告，差异为命令行覆盖默认船只的提示。
4. 47 张既有截图回放：4 张退出确认框全部识别，43 张负例没有误命中，最高负例分数 0.7200，保留阈值 0.78。两种退出确认框均通过生产感知和状态机驱动的数字零血、退出确认、回港、随机等待及下一场排队分流；开局步骤、输入和存储使用替身。
5. 补充生产配置、感知引擎、开局步骤执行器与状态机的截图回放。快速、完整两条开局路径中，实际画面已经到队列或战斗时都立即接续，旧序列被取消，只创建一次场次记录，不再返回额外点击。战斗截图使用铁公爵仍有 734 血的真实帧，验证的是进入战斗而非死亡退出。旧满血样本并非当前铁公爵身份配置，未把其未命中当成当前船只识别失败；改用匹配当前配置的实际样本完成回放。

## 仍需实机确认的范围

本轮没有启动托管、切换游戏前台、捕获新屏幕或发送真实输入。连续多场运行、快速匹配、游戏对退出与巡航选点的实际响应，以及 GUI、暂停和地图界面在真实切换中的时序仍由用户复测。现有过载自动动作和其它非核心功能没有新的实机证据，不更改其验收状态。运行中的旧进程不加载本次修改，测试前需关闭并重新启动本工具。
